多 Agent 对抗性审查 · 最终汇总
四个视角的 agent 交叉验证后，去重合并，按严重度排序。我之前的两轮审查只发现了表层问题，这轮挖出了多个致命级根因。

🔴 CRITICAL（必须立即修，数据丢失/安全漏洞）
C1. commit_chapter 永不提交，数据全部丢失
routes_generation.py:774 用了 with repo.unit_of_work(): 但 unit_of_work 的 __exit__ 里 _commit_or_flush() 走的是 flush() 不是 commit()（因为 _in_tx 还是 True）。整个 commit 事务被 db.close() 回滚，但端点返回 committed: True。StateChange/Event/RelationshipChange/ChapterCommit/伏笔更新全部不落盘。

三个 agent 都独立发现了这个或相关问题。

C2. API key 明文泄露 + SSRF 外泄
GET /api/config/llm 直接返回明文 api_key。POST /api/config/llm/test 允许用户传 base_url 但用服务端真实 key 发请求 → 攻击者构造 base_url=https://attacker.com，服务端就会把真实 key 发到攻击者服务器。全应用无认证。

C3. SQLite 外键约束未启用，所有 ondelete="CASCADE" 形同虚设
database.py 从未执行 PRAGMA foreign_keys=ON。所有外键级联声明都是摆设，删项目/角色/势力后留大量孤儿数据。

C4. SSE 无条件报 "completed"，即使生成失败
routes_chapters.py:83 在 stream 结束后无条件 yield {"status":"completed"}。即使走 end_failed（草稿为空/LLM 返回垃圾），前端也收到"完成"。用户以为生成成功但什么都没有。

C5. SSE error 事件字段名前后端不匹配
后端发 {"message": str(e)}，前端读 data.error → 永远 undefined。所有 LLM 错误信息（配额超限/超时）永远到不了用户，只显示通用"生成失败"。

🟠 HIGH（严重功能缺陷/数据不一致）
H1. 连点 10 次"生成" → checkpoints.db "database is locked"
checkpoints.db 跨项目共享、无 WAL、无 busy_timeout。并发生成必崩。

H2. 两套记忆系统产出不一致的上下文
老 CoreMemoryAssembler（自动生成用）vs 新 MemoryPackBuilder（编辑器 brief 用）——同一章走不同路径拿到完全不同的上下文，导致前后矛盾。

H3. 两套状态写入路径，事件流残缺
老 summarize_chapter 经 applier 写事件流；新 commit_chapter 直接写快照不写事件流。手动 CRUD 完全不写事件流。TruthEvent 自称"不可变追加支持 time-travel"，实际只覆盖 applier 一条路径，大部分变更丢失。

H4. unit_of_work 从不提交（C1 的根因）
repository.py:40 的 _commit_or_flush() 在 unit_of_work.__exit__ 时 _in_tx 仍为 True → 走 flush 不走 commit。docstring 说"退出统一 commit"是错的。applier 靠后面显式 db.commit() 兜底，但 commit_chapter 没有兜底。

H5. 角色改名/删除导致大量悬空引用
EntityAppearance/CharacterRelationship/EmotionArc/CharacterMatrix/StateChange/TruthEvent 全按角色名存。改名不改这些表 → 出场记录失效；删角色不清理 → 全部变孤儿。

H6. 全局 set_config 每请求重绑 engine + 跑 migrate_db
15 处调用，并发请求竞态改写全局 engine + 并发 ALTER TABLE → "database is locked" 或迁移半途。

H7. 伏笔状态机零校验，允许任意非法跳转
pending→resolved（跳过 planted）、resolved→planted（复活已回收）、任意字符串状态都能写入。

H8. 文件上传无大小/类型限制
file.read() 一次性全量读入内存，无 MAX_UPLOAD_SIZE。上传超大文件 → OOM；构造的 docx/pdf → 解析器 CVE 风险。

H9. LLM 端点无并发/速率限制
无认证 + 无限流，攻击者并发刷生成端点即可耗尽 LLM 配额产生大额账单。

# 对抗性多 Agent 审查报告

> 方法：六个独立 agent 视角，各自以"打翻这个项目"为目标取证。结论只认实锤，不认 commit message。

## **Agent 1 — 安全工程师（红队）**

结论：**这是个敞开的口子，部署到公网当天就被刷爆。**

- `app.py:11` CORS `allow_origins=["*"]`，且 `routes_chapters.py:52` SSE 是 `GET` 且无鉴权。任何人 `curl http://你的IP:8000/chapters/generate/stream?project_id=1&chapter=1&title=x` 就能烧你的 LLM 配额。配合 `config.yaml` 里真实 key（你前几轮终于换成 fake，但生产配置一旦填真 key），**跨站请求伪造 + 配额盗刷**一条龙。
- 零鉴权、零速率限制、零用户体系。`routes_bible.py` 全部 `Depends(get_repo)` 只校验 project_id 是否存在，不校验"你是不是这个项目的拥有者"。`GET /chapters/generate/stream` 连 project_id 都在 URL，任意项目可被任意人触发生成。多用户场景下 A 能生成 B 的章节、读 B 的圣经。
- `routes_generation.py` 把 LLM 原始返回 `raw[:200]` 直接塞进 `HTTPException(422, ...)` 回给前端——**LLM 输出未脱敏即外泄**，可能含被注入的 prompt、密钥片段、内部错误栈。这是信息泄漏。
- Electron 打包（`frontend/electron`）后端监听 `127.0.0.1`，看似本地安全，但 SSE/CORS `*` 意味着用户浏览器里任意恶意网页都能 fetch `http://127.0.0.1:8000` 读小说数据、触发生成。**桌面应用反而成了本地 SSRF 跳板**。
- `frontend/src/main.ts:7` `innerHTML` 模板拼接——目前是静态，但说明团队对注入不设防，后续若把任何 LLM 输出 innerHTML 进去就是存储型 XSS。

## **Agent 2 — 并发与事务专家**

结论：**SQLite + 这个 session 管理方式，第二个并发请求就崩，长 SSE 会话还会泄漏连接。**

- `routes_bible.py:22` `get_db` 每次 `SessionLocal()` 但 `try: yield db` 之后**没看到 `db.close()`**（截断处就断了，`finally: db.close()` 没出现）。会话不归还，SQLite 连接池耗尽，表现为"跑一阵就 500"。这是 P0 资源泄漏。
- 更严重：`routes_chapters.py` SSE 端点里 `db = SessionLocal()` + `runner = ChapterRunner(cfg, repo=repo)`，整个 SSE 生命周期（一次生成可能几分钟）**持有一个 session + 一个 sqlite 连接不释放**。WAL + `busy_timeout=5000` 只缓解写锁，但这个长连接在生成期间若 backend 别处要写同一个 db，就等 5 秒后 `database is locked`。同时 N 个用户并发生成 = N 个长连接锁死。
- `_commit_or_flush` 被 `applier.apply` 之外**到处直接调**（repository 里 30+ 处）。`unit_of_work` 的原子性承诺形同虚设：applier 在 `with unit_of_work()` 里调 handler，handler 内部又调 `_commit_or_flush`——但 `_commit_or_flush` 在 `_in_tx=True` 时只 flush 不 commit，看似对的；可 `applier.apply` 末尾还有一句兜底 `self.repo.db.commit()`（上几轮就存在），**绕过了事务边界直接提交**。一旦 handler 多步写中途失败，rollback 生效，但那个兜底 commit 在异常路径外执行——正常路径下把未完成的事务提前提交，跨 handler 的原子性被这一个 commit 打穿。spec 2.4"apply + 事件流原子性"在并发/异常混合下不成立。
- `ChapterRunner` 里 `SqliteSaver(self._saver_conn)` 用 `check_same_thread=False` 共享一个 sqlite 连接给 LangGraph checkpointer。`graph.ainvoke` 是 async，多个 `ainvoke` 并发跑在事件循环不同线程上共享同一连接——sqlite 连接非线程安全共享，轻则错乱重则损坏 checkpoints.db。

## **Agent 3 — LLM 系统可靠性专家**

结论：**所有"健壮性"都是单点串行假设，真实负载下一触即溃。**

- `LLMClient.generate` 每次调用 `async with httpx.AsyncClient()` **新建客户端**（`client.py`）。无连接池复用、无 keep-alive。高频生成（写+审+rewrite×3+polish+summarize，单章 6-8 次调用）每次握手 TLS，延迟和配额消耗都被放大。
- 重试逻辑只对超时/网络/429/503 退避，但**同一次 `generate` 内的三个 `except` 分支里，`429 quota` 直接 raise 不重试、普通 429 退避 4/8/16 秒**——可这退避在 SSE 长任务里会让单个节点阻塞 16 秒，前端 SSE 心跳超时断连，用户看到"卡死"。没有给 SSE 配置单独的超时/心跳策略。
- 整条流水线**零超时熔断**：`write→audit→rewrite` 循环最多 3 轮，每轮 1 次 write + 1 次 audit，单章最坏 6 次 LLM 调用串行。一次 600 秒 timeout × 6 = 1 小时一个章节。spec 自己写 `timeout_seconds: 300`，代码里 `LLMConfig.timeout=600`，且 graph 层无任何整体超时。`orchestration.max_iterations` 配置项存在但 graph 硬编码 3，配置形同虚设。
- `summarize_chapter` 的 JSON 解析 `re.search(r"\{.*\}", raw, re.DOTALL)`——贪婪匹配第一个 `{` 到最后一个 `}`。LLM 若在正文里带了大括号（网文常见：技能名`{烈焰}`、系统提示框），**整个摘要解析吃进正文垃圾**，`json.loads` 失败 `data={}`，摘要退化成 `content[:200]`，且**无日志、无状态标记**。质量滑坡静默发生。这正是 Agent 3 该挑的"静默降级"病。
- bge 这轮接了（上一 agent 视角已确认真调用），但 `_build_embedding_function` 失败回退 `None` 时，chromadb 用默认 MiniLM。**运行时无法知道当前用的是哪个**——没有把"实际生效的 embedding 模型"记进元数据或日志。长篇跑了一半换环境，召回质量突变却无任何可观测性。

## **Agent 4 — 测试与质量工程师**

结论：**89 个测试是绿色谎言，真实闭环一条没测。**

- 全仓 148 处 Mock/Fake，真实 LLM 集成测试 11 处但都不在 CI 关键路径。`test_orchestrator_write_review.py` 用 mock LLM 返回固定字符串，`test_orchestrator_nodes_m3.py:76` 只单测 `route_after_audit` 喂手造 state——**前几轮 write 失败短路"修了不生效"就是这么被测试盖过去的**：测试构造 `status:"failed"` 直接断言 `end_failed`，但从不跑真实 graph，所以 graph 里 `write→audit` 直连边的 bug 测试全绿。测试在验证"如果状态是 failed 会返回 end_failed"这个同义反复，不验证"write 失败后状态真的会是 failed 且走到 end_failed"。
- validator 这轮真接入了，但**有没有测试喂"带应埋伏笔但正文不含 ID 的草稿"验证它会被 critical 打回**？没有。所以 Agent 0（我上一轮）点的"伏笔检查反向惩罚"这种 P0 逻辑倒置，测试一个都抓不到。测试覆盖的是"validator 能被 import、能跑"，不是"validator 的判定是否正确"。
- `load_config` 不读 `auditor_llm`——**有没有测试 `load_config(config.yaml)` 后断言 `cfg.auditor_llm` 非空**？没有。`save_config` 能写、`load_config` 不读，这种不对称如果有 round-trip 测试一眼就能抓。说明配置层根本没有 round-trip 测试。
- `frontend/dist` 产物 448KB 的 `index-D5BjYDbV.js` 进没进 git？没（上轮确认 `git ls-files frontend/dist` 为 0）。但前端测试？`tests/` 全是 Python。**前端零测试**，40+ props 的 `Workspace` 组件、SSE 事件解析、状态机全靠人肉。这在前几轮"前端改坏 prompt 引号导致点击无响应"（git log `f4ac40b`）已经实锤出过事，仍无回归网。
- `frontend/src/counter.ts`、`vite.svg`、`typescript.svg` 脚手架残留至今没删——连最基础的"项目卫生"测试/CI 检查都没有。

## **Agent 5 — 领域专家（网文长篇）**

结论：**"200 万字自洽长篇"是营销话术，当前机制第 30 章后必漂移。**

- core memory 仍 `list_characters()` 全量注入（Agent 0 已点，本轮未改）。第 50 章、100 个角色时，`max_chars=8000` 被角色卡吃掉大半，**本章细纲（你上轮刚接通的）会被截断**。讽刺：你刚把规划注入生成，转头长篇下它第一个被角色列表挤掉。优先级设计倒置——细纲是本章硬约束，应是最高优先级保活，角色可裁。
- 卷级摘要这轮实现了 `get_volume_summary`，但 Agent 0 已确认**它没被任何生成流程调用**。我再加一刀：它返回的是"该卷最后 20 章摘要各截 100 字"，**这不是摘要，是目录**。长篇前情回顾需要的是"卷的主线发生了什么、关键转折、遗留悬念"的压缩叙事，给 LLM 生成时当背景。当前的拼接物塞进 prompt 只增加噪声不增加信息。spec 写"Summarizer agent 生成卷摘要"，这里没有任何 LLM 压缩，纯机械截断。
- `get_full_summary` 把 1000 章摘要全拉出来——第 500 章生成时 core memory 若调它，直接 OOM 级上下文。无任何分层裁剪策略（应是"近期详 + 卷级压 + 全书一句话"三级）。
- 伏笔只分单层 `foreshadow_id`（S/M/L 仅在命名规则 CSV 里提），但 `get_foreshadows_to_resolve` 按 `planned_resolve_chapter==chapter` 精确匹配。**长篇伏笔常跨卷延迟回收**（埋在卷一、卷三才回收），一旦实际回收章偏移，`to_resolve` 查不到，LLM 摘要也无人提示要回收它，伏笔永久悬挂。没有"逾期未回收伏笔"的巡检/告警。
- 题材参考资料（9 个 CSV）靠**关键词子串匹配**召回（`search.py`），`canonical_genre` 要求 `all(k in text for k in keywords.split("/"))`。用户填"都市异能修仙"会因为同时命中多个题材规则而返回第一条命中，参考资料混入不相关题材套路。长篇跨题材（如"科幻+悬疑"）时检索质量不可控。

## **Agent 6 — 架构与可维护性审计师**

结论：**架构分层正确，但分层间契约全是松散约定，已出现多处跨层穿透，正在腐化。**

- `routes_bible.py` 1319 行、`routes_generation.py` 929 行、`repository.py` 595 行——三个上帝文件。`routes_bible` 一个文件管 10 种资源 CRUD，任何一处改字段都要在千行文件里搜。`repository.py` 30+ 处 `_commit_or_flush` 散落各 `create_/update_/delete_`，事务边界被业务方法各自管理——这是**事务控制倒置**，本应由 service 层统一控事务，现在 dao 层自己 commit，service（applier）的 `unit_of_work` 反而要靠 `_in_tx` 标志位去"请求"dao 别 commit。标志位一旦漏设或并发错位，原子性即破。
- `nodes.py` 338 行同时承担：prompt 构造、文本清洗、JSON 检测、确定性审计调度、状态路由、摘要解析、伏笔回收、角色状态更新。**一个文件里混了 4 个关注点**。`summarize_chapter` 一个函数干了 6 件事，且每件都有静默 `except: pass`/`except: data={}`。这是未来 bug 的温床。
- 配置层契约破裂（Agent 0 主点）：`Config.auditor_llm` 字段存在、`save_config` 序列化它、`runner` 消费它、`yaml` 有它，**唯独 `load_config` 不反序列化它**。四个接点对一个漏点，这是典型的"多人协作/多轮迭代下契约失配"。没有 schema 校验或 round-trip 测试兜底。
- `Delta.target` 枚举声明 8 个值，applier 只实现 4 个 handler，其余 4 个（`emotion_arc`/`subplot`/`character_matrix`/`world_setting`）声明即 raise。**类型系统在撒谎**——schema 允许的值，运行时一半是炸弹。要么收窄枚举到已实现的，要么补 handler，当前是"看起来支持其实不支持"的最坏状态。
- 前端 `App.tsx` → `Workspace` 传 40+ props，即便有 zustand store。**store 存在却不用它传递数据，仍手传**——架构上引入了状态管理库但没贯彻，形成了"半 store 半 props"的混合态，比纯 props 更难维护（两套真相源）。

## **跨 Agent 共识（6 个视角都命中的）**

1. **契约失配是系统性病灶**：auditor_llm 四接一漏、Delta 枚举半实现、save/load 不对称、`_commit_or_flush` 跨层散落。不是单点 bug，是缺少 schema/round-trip/契约测试的工程文化问题。
2. **静默降级泛滥**：摘要解析失败 `data={}`、bge 回退无记录、伏笔回收 `except: pass`、润色失败用原稿、validator 死活不报。系统会**无声地变差**，用户和开发者都看不到。
3. **测试给虚假信心**：所有 P0 逻辑倒置（伏笔反向惩罚、write 短路失效、auditor_llm 不生效）测试全绿。测试在验证实现而非行为。
4. **长篇能力仍三根空柱**：中文 embedding 默认不装不生效、卷级摘要实现了不调用、角色全量注入。200 万字目标无一处工程支撑到位。
