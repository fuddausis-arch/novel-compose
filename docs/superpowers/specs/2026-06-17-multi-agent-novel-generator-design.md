# 多 Agent 自动小说生成系统 · 设计 Spec

> 状态：设计阶段（待用户通审）
> 日期：2026-06-17
> 范围：阶段 1（MVP，单卷连贯跑通）；架构按 200 万字长篇一次设计

---

## 0. 背景与约束

### 0.1 目标
构建一个多 agent 协作的网文自动生成系统：agent 自动跑创作流水线，人在关键节点（大纲/卷末/定稿）审核把关，产出接近签约可读水平的网文长篇。

### 0.2 核心约束（用户已确认）
| 维度 | 选择 |
|---|---|
| 自动程度 | 关键节点把关（人审大纲/卷末/定稿） |
| 目标规模 | 200 万字长篇（架构按此设计，分阶段交付） |
| 代码基座 | 完全重起炉灶，技术栈开放 |
| 质量预期 | 接近签约可读水平（多轮自检 + 关键节点人审） |
| 方法论来源 | 借鉴用户既有工作流 v2.0（8 库结构/写前-写中-写后循环/15 维度审计/文风检测/伏笔生命周期），不导入旧作品内容 |

### 0.3 四条铁律（来自用户项目书 + 调研）
1. **写审分离**：创作者和审阅者是独立 agent，审阅者不看生成过程上下文
2. **数据驱动**：agent 间通过严格 JSON 协议通信，不依赖隐式上下文
3. **反馈循环 ≤3 次**：避免无限循环，超限交人工
4. **持久化存储**：所有中间状态写盘，不依赖内存，崩溃可恢复

### 0.4 调研基础
本设计综合调研了以下开源项目与论文：
- **qianbkk/novel_AI**（Python+LangGraph 7 节点，技术栈 1:1，作骨架蓝图）
- **InkOS / Narcooo/inkos**（7.3k★，三层权威记忆 + 模型只产 delta + 审计只修 1 次）
- **knoai/knowrite**（Temporal Truth Database 事件溯源 + Fitness 五维 + Editor 双通过审 + Prompt 自演化）
- **CenitStoryTeller**（Acid Test 四维：物理/心理/环境/化学）
- **MemGPT/Letta**（分层记忆：core/archival/recall + self-edit）
- **Generative Agents**（记忆检索三因子 recency×importance×relevance + reflection）
- **Re3 / DOC**（plan 常驻 + 每步重注入状态 + rerank + 事实 edit）
- 视频参考：古法编程-小周《多Agent自动写小说流程》（写审分离/五阶段/数据协议/反馈≤3次）

## 1. 整体架构与技术栈

### 1.1 技术栈
| 层 | 选型 | 理由 |
|---|---|---|
| 编排引擎 | Python + LangGraph | 状态图 + checkpoint 断点续跑 + interrupt 人审节点，为长流程+人审+可恢复量身定做 |
| LLM 调用 | OpenAI 兼容接口（httpx 直连 + 重试/降级/超时） | 不绑死厂商；多模型分层降成本 |
| 圣经存储 | SQLite（结构化）+ Chroma（向量检索） | 结构化存权威状态；向量库存章节摘要做检索召回 |
| 后端服务 | FastAPI + SSE 流式 | 生成进度/agent 状态推送/人审批注 API |
| 前端 | React + Vite（Web 控制台） | 长任务后台常驻 + 断点续跑 + 多设备查看 |
| 进程模型 | 本地 Python 服务 + 浏览器控制台 | 服务化，可后台常驻、可恢复 |

### 1.2 整体架构
```
┌─────────────────────────────────────────────────────┐
│  Web 控制台（React）                                  │
│  生成驾驶舱 │ 人审工作台 │ 圣经浏览器 │ 章节阅读器    │
└────────────────────┬────────────────────────────────┘
                     │ SSE / REST
┌────────────────────┴────────────────────────────────┐
│  FastAPI 服务层                                       │
│  任务管理 │ 人审批注 │ 圣经读写 API │ 流式输出 │ 日志  │
└────────────────────┬────────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────────┐
│  LangGraph 编排引擎（状态机 + checkpoint + interrupt）│
│  总编→设定组→大纲师→[人审①]→写手→审校→润色→[人审②]  │
│       每节点产出按数据协议持久化，反馈循环 ≤3 次       │
└────────────────────┬────────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────────┐
│  「小说圣经」记忆层（三层记忆 + 事件溯源）             │
│  Core：常驻上下文（角色/大纲/力量/伏笔子集）           │
│  Archival：向量库（全章节切块 + 设定条目）             │
│  Summary Tree：章→弧→卷→全书分层摘要                  │
│  Recall：全量原文 + 事件时间线                         │
└─────────────────────────────────────────────────────┘
```

### 1.3 分阶段交付
- **阶段 1（MVP，本 spec 范围）**：单卷（~30-50 章）连贯跑通
- 阶段 2：多卷扩展 + 圣经语义检索成熟 + 断点续跑稳定
- 阶段 3：200 万字可持续 + 一致性退化防护 + 成本控制

架构决策保证不挡阶段 2/3 的路（如圣经 schema 一开始就为长篇设计、事件流第一版就上）。

## 2. 小说圣经 Schema（系统命门）

### 2.1 三层记忆架构
```
Core Memory（常驻上下文，~2-4k token，每章注入）
  - 当前活跃角色卡（出场/将要出场）
  - 当前卷大纲 + 当前弧任务单
  - 当前力量体系快照（等级/能力/进度）
  - 未回收的关键伏笔列表（仅相关子集）

Archival Memory（向量库 Chroma，按需检索）
  - 全量章节切块向量化
  - 世界设定条目
  - 检索：recency × importance × relevance 三因子打分召回

Summary Tree（分层摘要，长程弧光）
  - 章摘要 → 弧摘要 → 卷摘要 → 全书摘要
  - 每层有损压缩，固定大小，不随字数增长

Recall（全量日志，精确回溯，不进上下文）
  - 完整章节原文 + 事件时间线
```

**为什么三层**（调研铁律）：纯向量库召回过时片段污染当前；纯结构化丢描写质感；纯摘要树丢伏笔。200 万字下任何单层都会崩。三者互补：向量解决"找得到"，结构化解决"对不对"，摘要树解决"记得住全局"。

### 2.2 结构化权威状态（9 库，借鉴用户 8 库 + InkOS + knowrite）

| 库 | 对应用户 8 库 | 存什么 | 写入时机 |
|---|---|---|---|
| `characters` | 主要人物卡 | 角色 id/姓名/身份/能力等级/位置/情绪/已知信息/关系/秘密 | 设定阶段建，每章后 diff 更新 |
| `world_settings` | 核心设定 | 分类条目（世界观/力量体系/势力/地点/规则） | 设定阶段建，偶发扩展 |
| `outlines` | 细纲 | 卷→弧→章三级，含 act/title/summary/order | 总编+大纲师建 |
| `foreshadows` | 伏笔与道具追踪 | id/埋下章/描述/依赖/状态(待埋/已埋/发展中/已回收/已废弃)/计划回收章 | 大纲师规划，写手埋设，审校校验回收 |
| `foreshadow_implants` | 核心伏笔早期植入方案 | 每个伏笔的具体呈现方式 | 大纲师规划 |
| `chapter_summaries` | 章节摘要历史 | 时间地点/核心事件/出场人物/情感变化/伏笔动态/支线进展/章节钩子/字数 | 每章后 summarizer 生成 |
| `emotion_arcs` | 情感弧线追踪 | 角色×章节情感状态变迁 | 每章后 diff |
| `subplot_board` | 支线进度板 | 各故事线状态/推进度/关联角色/预计回收章 | 每章后 diff |
| `character_matrix` | 角色交互矩阵 | 角色相遇记录/知识边界/信息传播 | 每章后 diff |

### 2.3 事件溯源（knowrite 核心贡献，长篇一致性最对症）

除"当前状态快照"外，追加不可变事件流，支持 time-travel 查询：
```python
class TruthEvent:
    id: int
    chapter: int
    type: Literal["foreshadow_planted", "foreshadow_resolved",
                  "character_state_change", "resource_change",
                  "relationship_change", "timeline_event"]
    entity_id: str
    payload: dict
    timestamp: datetime
```

**为什么需要事件流**：200 万字下"第 350 章这个法宝怎么流转到反派手里的"这种追溯，快照答不了，事件流能。审校发现矛盾时能精确回溯到引入冲突的章节。第一版就上，避免后补迁移。

### 2.4 写入协议（防崩坏命门）
```
Agent 产出 → JSON delta（结构化变更）
          → pydantic 校验（schema + 业务规则）
          → 校验失败：拒绝，打回 agent 重产
          → 校验通过：immutable apply 到快照 + 追加事件流
          → 同步更新向量库 + 摘要树
```

**铁律**：模型绝不直接写 markdown/正文文件当真相源。正文是产出物，圣经才是真相。根治用户原手工维护 8 markdown 库的"格式漂移 + 失同步"痛点。

## 3. Agent 流水线与角色

### 3.1 七角色流水线

> 术语：**弧（Arc）** = 一卷内的一段情节单元，通常 5-15 章，有独立的小高潮和起承转合。结构层级：全书 → 卷 → 弧 → 章。一个 Agent 角色可对应一个或多个 LangGraph 节点。
```
[总编 Planner]     全书→卷→弧三级规划，节奏曲线/爽点分布/伏笔布局
      │            产出：卷大纲、弧任务单、伏笔台账规划
      ▼
[设定组 Architect] 世界观/角色/力量体系/势力 → 写入圣经核心库
      │            产出：结构化设定 delta（经校验写入）
      ▼
[大纲师 Outliner]  本卷章节细纲，标注每章伏笔埋设/回收计划
      │            产出：章节细纲 + 伏笔植入方案
      ▼
   ★人审节点①：大纲审核（用户可改/批注/通过）
      ▼
[写手 Writer]      逐章生成正文。写前：检索相关切片注入（core+archival）
      │            产出：章节草稿
      ▼
[审校 Auditor]     独立审阅（不看生成过程），15维+Fitness+Acid Test
      │            产出：评分报告 + 修订建议
      │  不达标 → 回 Writer 重写（≤3次）
      │  达标 → 进润色
      ▼
[润色师 Polisher]  文风优化 + AI痕迹清除 + 语言润色
      │            产出：定稿章节
      ▼
   ★人审节点②：卷末/定稿审核
      ▼
[记忆官 Summarizer] 抽取本章 delta：章节摘要/情感弧线/伏笔动态/事件流
      │            产出：结构化 delta（经校验写入圣经，同步向量库+摘要树）
      ▼
   进入下一章 / 下一卷
```

### 3.2 设计依据
- **写审分离**（铁律）：Writer 和 Auditor 独立，Auditor 只看成稿+圣经，不知生成过程，防自我背书
- **模型分层**（novel_AI/CenitStoryTeller）：创作用强模型高温（Claude Sonnet/GPT-4o），审校用低成本模型低温（DeepSeek/GPT-4o-mini），不同 agent 配不同模型——防背书又控成本。调研估 ~$60 跑完 300 万字
- **Summarizer 单独成 agent**（MemGPT self-edit）：记忆更新独立工序，不混审校，保证 delta 抽取专注可校验
- **人审两处够用**：大纲（防方向跑偏）+ 卷末（防质量崩坏），不过度打断自动流

### 3.3 Agent 间通信协议（数据驱动铁律）
每个 agent 产出严格 JSON schema，不靠隐式上下文：
```json
{
  "agent": "writer",
  "stage": "chapter_draft",
  "chapter": 7,
  "artifacts": [{"type": "chapter_draft", "content": "..."}],
  "notes": "给下游 auditor 的说明",
  "status": "completed"
}
```

## 4. 写审循环与人审节点

### 4.1 写审循环（≤3 次，铁律）
```
Writer 产出草稿
  → Auditor 审阅打分
    → 达标(≥阈值) → 进 Polisher
    → 不达标 → 打回 Writer，附修订建议 + 历史审阅痕迹（第2轮起注入）
      → 重写 → 再审
        → 仍不达标，循环 ≤3 次
          → 第3次仍不达标 → 挂起，触发人审③（人工介入）
```

### 4.2 人审节点（LangGraph interrupt）
- 节点①（大纲）：流程暂停，前端弹大纲审核界面，用户改/批注/通过 → resume 传回决策
- 节点②（卷末）：整卷定稿后暂停，用户通审 → resume
- 节点③（重写失败）：人工决策"继续重写/跳过本章/手动改"

### 4.3 断点续跑（LangGraph checkpoint）
- SqliteSaver 持久化每个节点执行后状态
- 进程崩溃/关机 → 重启从最近 checkpoint 恢复，不丢已生成章节
- 200 万字跑几十上百小时，这是刚需

## 5. 审计维度

### 5.1 融合审计清单
融合用户 15 维 + knowrite Fitness 五维 + CenitStoryTeller Acid Test 四维：

| 类别 | 维度 | 来源 |
|---|---|---|
| 一致性 | 设定一致性、伏笔准确性、时间线连贯、地理正确性、信息边界(角色只说知道的)、资源合理性 | 用户15维 + knowrite |
| 人物 | 情感连续性、人物OOC(MAR法则)、对话真实性、视角一致性 | 用户15维 + Acid Test心理维 |
| 情节 | 支线推进度、节奏控制、爽点分布、读者期待管理(钩子)、大纲偏离度 | 用户15维 + Fitness |
| 文风 | 文风统一、AI标记词检测 | 用户15维 |
| 物理 | 身体/伤/年龄/生死一致性(死后不能行动) | Acid Test物理维 |
| 环境 | 符合地点时代+lore | Acid Test环境维 |
| 关系 | 关系有铺垫不突兀 | Acid Test化学维 |

### 5.2 评分机制（knowrite 双通过）
- 关键维度（设定一致性/OOC/伏笔/信息边界/物理）任一不过 → 直接打回重写
- 次要维度通过率 ≥80% → 通过
- Fitness 总分 = 字数/重复率/审阅通过率/读者分/大纲偏离 加权

**为什么融合三方**：用户 15 维偏网文创作实操，knowrite 偏量化治理，Acid Test 偏逻辑硬伤——互补，单用任套有盲区。

## 6. 数据持久化与可恢复性

### 6.1 存储布局
```
project_data/
├── bible.db              # SQLite：9 结构化库 + 事件流表 + checkpoint
├── chroma/               # 向量库：章节切块 + 设定条目
├── chapters/             # 正文产出（按卷/章分文件，markdown）
│   └── 卷一/第007章_标题.md
├── artifacts/            # 每个 agent 每次产出 JSON（审计追溯）
│   └── ch007/writer_v1.json, auditor_v1.json, ...
├── snapshots/            # 每章定稿后圣经快照（time-travel 回滚）
│   └── ch007/bible.json
└── logs/                 # 运行日志（token/耗时/错误）
```

### 6.2 可恢复性三层
1. **节点级**：LangGraph checkpoint，崩了从最近节点恢复
2. **章节级**：每章定稿后存圣经快照，章节出问题可回滚到上一章状态
3. **版本级**：Writer 每次重写存 artifacts，可对比 v1/v2/v3 草稿

**为什么三层**：200 万字长流程失败点必然（API 崩/模型抽风/人审改主意）。无回滚只能从头重来，不可接受。

## 7. 前端控制台

### 7.1 四个核心界面（React + Vite + SSE）
1. **生成驾驶舱**：当前章节/agent 状态/流水线进度/实时流式输出/token 成本
2. **人审工作台**：大纲审核/卷末审核/重写失败决策，支持批注/改/通过
3. **圣经浏览器**：9 库可视化浏览（角色卡/伏笔台账/时间线/摘要树），可编辑
4. **章节阅读器**：已生成章节阅读，按卷/章导航

### 7.2 技术选择
- **Web 不 Electron**：长任务后台常驻 + 断点续跑 + 多设备查看 + 服务化潜力
- **SSE 不 WebSocket**：流式单向推送够用，更简单，断线自动重连

## 附录 A：技术风险与未决项

1. **200 万字未验证区**：Re3/DOC/InkOS 演示规模均 ≤万字级，分层粒度/台账 schema/摘要树深度需自行压测。这是核心技术风险。
2. **成本**：调研估 ~$60/300 万字，但 Fitness 权重、重写频次、向量库大小需标定。
3. **模型分层具体配置**：哪个 agent 用哪个模型/温度，需实验调参。
4. **AGPL 注意**：InkOS/knowrite/AI_NovelGenerator 均 AGPL-3.0，借鉴思路不抄代码，商用需评估。
5. **审计维度权重**：15 维 + Fitness + Acid Test 融合后，各维度权重和阈值需跑数据标定。
